# PKT-1 · Decision record

Choices [PKT-1](../../plan/solo-budget/packets/PKT-1.md) left open, and why each went the way it did.

## Config keys

1. **`tierCap` accepts what the other review limits accept.** It goes through the same `$whole` check as `maxRounds`, so `2`, `3`, `"2"`, `" 3 "` and `2.0` load as `[int]`. Anything else stops with the message the packet gives: `0`, `1`, `4`, `2.5`, `"two"` and `true` (the `[bool]` isn't a whole number). So does a whole number too large for an `[int]`, such as `3000000000`: `$whole` used to throw a raw conversion error on one, for `maxRounds` too, and now returns no number. Get-PwConfig always fills the key on its copy of `review`, so readers see `$null`, `2` or `3` even when an old config has no `tierCap` line. The shared defaults keep `$null`, and a test checks that.
2. **Get-PwConfig doesn't check `maxCreditsPerPacket` or `models.agents`.** The ceiling is checked where it is used, as the packet says. `models.agents` follows the same rule, because board and progress never read `models` (review notes, workstream 1). So a typo in either can't stop the board. Get-PwCreditCeiling and Get-PwAgentModelClass each stop on their own key. A test runs `board show` and `progress.ps1 -Json` with both keys broken.
3. **Get-PwCreditCeiling takes only JSON numbers.** It accepts an int, a long, a double or a decimal that is above zero. It refuses a quoted `"1500"`, unlike `tierCap`, because the packet lists "a string" among the values that stop it. NaN and infinity are refused too, though JSON can't express them. If `budget` isn't a table, or has no `maxCreditsPerPacket`, the result is `$null` (no ceiling). A size table is read with the size's case folded (`"m"` counts as `M`, and `-Size m` works), as `sizes` and `creditsPerRun` already are. A table that names one size twice, by case, stops. In a size table, a missing size and a bad value give the same message, which names the size that was asked for. A table may set fewer than three sizes: it only fails for the size that is missing. A list is refused, a one-item list included (`{ "M": [1300] }`). `-Size` takes only `S`, `M` or `L`, in either case.
4. **Get-PwAgentModelClass checks every `models.agents` entry on every call,** not only the agent it was asked about. A bad entry then fails the first reader, whichever agent that reader asks about. Agent names and class names are matched case-sensitively: agent names are file names, and the classes are the template's lower-case keys. Get-PwConfig puts `models.agents` back as written after its merge. The merge copies it into a table that folds case, so a key such as `PACKET-DISPATCHER` beside `packet-dispatcher` would vanish before the check. This only keeps the table as written; it doesn't check it. A `models.agents` that isn't a table stops with a message of its own, an empty or one-item list included, and `-Models $null` means the kit's classes. The function never reads `models.strong`, `standard` or `light`. Those lists stay with the installer (PKT-4).
5. **`$script:AgentModelClass` is an ordered table** in the order install.ps1 lists the agents. A test compares it, and the function's answers, with install.ps1's own table, so if the two drift apart the test fails. The installer itself isn't changed (that is PKT-4).
6. **`models` in the defaults copies the template's three lists,** plus `agents = @{}`. A test checks that the defaults' lists match the template's. Nothing in board, progress or review reads them yet.
7. **`$script:KitLenses` is a `[string[]]` in alphabetical order,** the order of the lens files. A test compares it with the base names of `skills/packet-review/lenses/*.md`, so adding or removing a lens without updating the list fails the run.

## Test-case folder

8. **`-CasesPath <folder>` runs only that folder's case files.** It skips the main suite and prints the same summary line. This is how the runner's own behaviour gets tested without running the 243-test suite again inside itself: counting, a throwing file, variable isolation, ordinal order and an empty folder. A folder that doesn't exist stops the run with exit 2, so a typo can't read as a pass. In the default run a missing `tests/cases/` folder just means no case files. The default run is unchanged, and `tests/cases/` runs after the suite.
9. **The loop lives in `Invoke-CaseFiles`.** It prints a `cases/<file>` header before each file, and nothing at all when there is no case file. A file that throws counts as one `FAIL cases/<file> ran to the end`, with the message and stack trace. The current directory is put back after each file, whatever the file did. Only `*.tests.ps1` files run, sorted with `StringComparer.Ordinal`, so `B…` runs before `a…` on every platform.
10. **The sample phase moved into `Write-SamplePhase`,** which both the suite and New-CaseRepo call. That way New-CaseRepo builds the same phase and doesn't keep a second copy. The function writes under `$repo` as found in the caller's scope (PowerShell looks variables up through the callers), so the suite's own setup is unchanged.
11. **The sample W0 packet's target is now `2026-10-31`.** `New-Packet` built `2026-11-0<wave>`, which made PKT-01's target `2026-11-00`, an invalid date. `progress.ps1` stops on that (`ParseExact`) once PKT-01 isn't done. The suite never hit it, but a fresh New-CaseRepo repository does, and the packet requires `progress.ps1 -Json` to exit 0 there. Only W0 changes. Every base test still passes, and none of them reads that date.
12. **New-CaseRepo puts its origin next to the repository,** as `<repo>-origin`, and Remove-CaseRepo removes both. `-Keep`, or the run's own `-Keep`, keeps both and prints the path. Every git call in New-CaseRepo stops on failure, so a broken helper fails as a thrown case file, not as a confusing assert later on. The config is the template's, with `repo = example/sample` and `board.provider = local`. Unlike the suite, it adds no `deepPaths`.
13. **The grep scans every `*.ps1` in `tests/cases/`** for two things. One is a `$script:` assignment (`=`, `+=` and the like, `++`, `--`, `Set-Variable … -Scope Script`). The other is a dot-sourced script: a `.` followed by a variable, a parenthesis, a quote or a `.ps1` path, at the start of a line or after `;`, `{`, `(`, `|` or `&&`. Reading a `$script:` variable is allowed. A test runs the dot-source rule on sample lines, including near misses such as `1.5` and a sentence's full stop.
14. **Kit code runs through `Invoke-CaseProbe` in `run-tests.ps1`,** never dot-sourced into the run. The helper writes a temporary script that dot-sources PacketWorkflow.ps1, then the caller's code, runs it in a child `pwsh` in the current directory, and returns what Invoke-Kit returns. Dot-sourcing a kit script in a case file would assign the kit's `$script:` variables (`Defaults` among them) in the runner's scope, where every later case file would see them; the architecture review showed it. The helper started as a local function in config-keys and moved to the runner so that later packets have one. PKT-7's Consumes line ("only dot-sources `PacketWorkflow.ps1`") should read "runs `PacketWorkflow.ps1` through `Invoke-CaseProbe`".

## Added at the owner's request (outside Owns)

15. **A Target that isn't a real date is rejected, not crashed on.** This answers open question 1 in the PR. The new `ConvertTo-PwDate` in PacketWorkflow.ps1 parses yyyy-MM-dd strictly. progress.ps1 now stops with `<ID> (<path>): Target must be a date as yyyy-MM-dd (got '…')` and exits 2 through its `PwError` handler. Before, it threw a raw `ParseExact` exception with a stack trace. `Test-PwPacket`, which validate-packets and board sync both use, now refuses days that don't exist, such as `2026-11-00` and `2026-02-30`. It gives the same message it already gave for a wrong shape. progress stops rather than skipping the packet, because a late list that quietly leaves a packet out would read as a pass. The tests are in `tests/cases/target-dates.tests.ps1`. The owner asked for this change in the PR's review and added `skills/packet-progress/scripts/progress.ps1` and `tests/cases/target-dates.tests.ps1` to PKT-1's Owns in a separate plan PR. A test now also checks the days progress.ps1 computes from a valid Target (DaysLate, DaysLeft), not only its exit code.

16. **Lens review.** The architecture, correctness and tests reviews of the PR led to decisions 1, 3, 4, 8, 13 and 14 as they now read, and to tests that `Remove-CaseRepo` removes or keeps both directories, that a quoted `"1500"` ceiling is refused, and that the default run's case loop prints nothing without case files.
