# PKT-1 · Decision record

Choices [PKT-1](../../plan/solo-budget/packets/PKT-1.md) left open, and why each went the way it did.

## Config keys

1. **`tierCap` accepts what the other review limits accept.** It goes through the same `$whole` check as `maxRounds`, so `2`, `3`, `"2"`, `" 3 "` and `2.0` load as `[int]`. Anything else stops with the message the packet gives: `0`, `1`, `4`, `2.5`, `"two"` and `true` (the `[bool]` isn't a whole number). Get-PwConfig always fills the key on its copy of `review`, so readers see `$null`, `2` or `3` even when an old config has no `tierCap` line. The shared defaults keep `$null`, and a test checks that.
2. **Get-PwConfig doesn't check `maxCreditsPerPacket` or `models.agents`.** The ceiling is checked where it is used, as the packet says. `models.agents` follows the same rule, because board and progress never read `models` (review notes, workstream 1). So a typo in either can't stop the board. Get-PwCreditCeiling and Get-PwAgentModelClass each stop on their own key. A test runs `board show` and `progress.ps1 -Json` with both keys broken.
3. **Get-PwCreditCeiling takes only JSON numbers.** It accepts an int, a long, a double or a decimal that is above zero. It refuses a quoted `"1500"`, unlike `tierCap`, because the packet lists "a string" among the values that stop it. NaN and infinity are refused too, though JSON can't express them. If `budget` isn't a table, or has no `maxCreditsPerPacket`, the result is `$null` (no ceiling). In a size table, a missing size and a bad value give the same message, which names the size that was asked for. A table may set fewer than three sizes: it only fails for the size that is missing. `-Size` takes only `S`, `M` or `L`.
4. **Get-PwAgentModelClass checks every `models.agents` entry on every call,** not only the agent it was asked about. A bad entry then fails the first reader, whichever agent that reader asks about. Agent names and class names are matched case-sensitively: agent names are file names, and the classes are the template's lower-case keys. A `models.agents` that isn't a table stops with a message of its own, and `-Models $null` means the kit's classes. The function never reads `models.strong`, `standard` or `light`. Those lists stay with the installer (PKT-4).
5. **`$script:AgentModelClass` is an ordered table** in the order install.ps1 lists the agents. A test compares it, and the function's answers, with install.ps1's own table, so if the two drift apart the test fails. The installer itself isn't changed (that is PKT-4).
6. **`models` in the defaults copies the template's three lists,** plus `agents = @{}`. A test checks that the defaults' lists match the template's. Nothing in board, progress or review reads them yet.
7. **`$script:KitLenses` is a `[string[]]` in alphabetical order,** the order of the lens files. A test compares it with the base names of `skills/packet-review/lenses/*.md`, so adding or removing a lens without updating the list fails the run.

## Test-case folder

8. **`-CasesPath <folder>` runs only that folder's case files.** It skips the main suite and prints the same summary line. This is how the runner's own behaviour gets tested without running the 243-test suite again inside itself: counting, a throwing file, variable isolation, ordinal order and an empty folder. The default run is unchanged, and `tests/cases/` runs after the suite.
9. **The loop lives in `Invoke-CaseFiles`.** It prints a `cases/<file>` header before each file, and nothing at all when there is no case file. A file that throws counts as one `FAIL cases/<file> ran to the end`, with the message and stack trace. The current directory is put back after each file, whatever the file did. Only `*.tests.ps1` files run, sorted with `StringComparer.Ordinal`, so `B…` runs before `a…` on every platform.
10. **The sample phase moved into `Write-SamplePhase`,** which both the suite and New-CaseRepo call. That way New-CaseRepo builds the same phase and doesn't keep a second copy. The function writes under `$repo` as found in the caller's scope (PowerShell looks variables up through the callers), so the suite's own setup is unchanged.
11. **The sample W0 packet's target is now `2026-10-31`.** `New-Packet` built `2026-11-0<wave>`, which made PKT-01's target `2026-11-00`, an invalid date. `progress.ps1` stops on that (`ParseExact`) once PKT-01 isn't done. The suite never hit it, but a fresh New-CaseRepo repository does, and the packet requires `progress.ps1 -Json` to exit 0 there. Only W0 changes. Every base test still passes, and none of them reads that date.
12. **New-CaseRepo puts its origin next to the repository,** as `<repo>-origin`, and Remove-CaseRepo removes both. `-Keep`, or the run's own `-Keep`, keeps both and prints the path. Every git call in New-CaseRepo stops on failure, so a broken helper fails as a thrown case file, not as a confusing assert later on. The config is the template's, with `repo = example/sample` and `board.provider = local`. Unlike the suite, it adds no `deepPaths`.
13. **The `$script:` grep scans every `*.ps1` in `tests/cases/`.** It looks for an assignment (`=`, `+=` and the like, `++`, `--`) and for `Set-Variable … -Scope Script`. Reading a `$script:` variable is allowed.
14. **The case file probes PacketWorkflow.ps1 in child `pwsh` processes,** never by dot-sourcing it into the run. Dot-sourcing would assign the kit's `$script:` variables in the runner's scope.

## Not changed

- review-scope doesn't use `tierCap` yet (PKT-3). No credit rate changed (PKT-7). The installer is untouched (PKT-4). No existing test moved into `tests/cases/`.
- review-scope's JSON for the suite's 21 sample diffs is byte-identical to the base's, once commit SHAs are set aside. The one exception is the order of names inside one `LensReasons` string (the diff that adds security, correctness and concurrency). That order already changes between two runs of the base: Merge-PwHashtable builds plain hashtables, and .NET randomises string hashes per process. Making it stable is a separate change.
