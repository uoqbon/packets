# PKT-4 · Decision record

Choices [PKT-4](../../plan/solo-budget/packets/PKT-4.md) left open, and why each went the way it did.

## The solo overlay

1. **`templates/packet-workflow.solo.json` holds the six keys of the packet's table and nothing else:** `models.agents`, `review.maxRounds`, `review.lensesPerReviewer`, `review.shouldFixPassFromRound`, `review.tierCap` and `budget.maxCreditsPerPacket`. It has no model lists and no `creditsPerRun`, so those come from the default template and can't drift from it. The ceiling is the owner's answer to question 4: S 950, M 1,500, L 2,200, on PKT-7's GPT-6.1 Sol rates, which the overlay inherits. A test checks the file's key paths exactly, so a key added to the overlay by mistake fails the run.
2. **The installer merges the overlay with a function of its own, `Merge-Overlay`, not `Merge-PwHashtable`.** `Merge-PwHashtable` builds a plain `@{}`, which loses the template's key order. `Merge-Overlay` writes into a fresh parse of the template (`ConvertFrom-Json -AsHashtable` gives an ordered table), key by key. A table merges into a table; anything else replaces the value where it stands. So `review.maxRounds` stays between `review` and `maxParallelLenses`, and `budget.maxCreditsPerPacket` replaces `null` in place. A key the template lacks would go at the end; the overlay has none. The merge runs before `repo` and the default branch are filled in, so those are filled the same way for both profiles. A test compares the written config with the template, with those six values set in place, as JSON text, so the order is checked as well as the values.
3. **`-Profile` takes `default` or `solo`, in any case** (`[ValidateSet]`; the value is lower-cased). Anything else is refused by PowerShell before the script runs, so nothing is written. `default` is the template alone, as before this packet, and is the default.

## An existing config

4. **On an existing config, `-Profile` never writes the config.** With `solo`, it compares each of the overlay's settings with the config and lists those that differ, as `path: config -> overlay` lines, for example `review.maxRounds: 3 -> 2`. It walks into a table only where both sides are tables, so `models.agents.packet-dispatcher: (not set) -> "standard"` is listed beside a config's own `models.agents` entries without naming them, and one differing size reads `budget.maxCreditsPerPacket.M: 1200 -> 1500`. Values are compared as compact JSON, case-sensitively, so a quoted `"2"` is listed as differing from `2`: the line shows exactly what the overlay would write. A key the config doesn't set reads `(not set)`. Keys the overlay doesn't hold (`repo`, the board, the model lists) are never compared. If nothing differs, it says the config already has the profile's settings. `-Profile default` on an existing config says nothing about it.
5. **The arrow is ASCII (`->`), not `→`.** The packet's example uses `→`. The installer's output goes through the console's encoding, which on Windows isn't always UTF-8, so an ASCII arrow reads the same everywhere.
6. **The agents follow the config, not the profile.** On an existing config, `-Profile solo` doesn't move the dispatcher: its class comes from the config's `models.agents`, as on any run. The listed `models.agents.packet-dispatcher` line is how the owner learns to move it.

## A class per agent

7. **The installer dot-sources `skills/packet-board/scripts/PacketWorkflow.ps1` and uses `$script:AgentModelClass` and `Get-PwAgentModelClass` from it, and nothing else.** It never calls `Get-PwConfig`, which would refuse a new config before its `repo` is filled in (Dispatcher notes). The library is dot-sourced at the top, so the vendored-kit layout (`install.ps1` beside `skills/`) is all it needs, as before.
8. **Each agent's class is resolved once, right after the model lists are read, and before anything is written.** `Get-PwAgentModelClass` checks every `models.agents` entry on every call (PKT-1, decision 4), so the first call stops on a bad entry. The installer catches its `PwError`, writes `install.ps1: config: models.agents.… Nothing was written.` to stderr and exits 2. That follows CONTRIBUTING's "exit 2 on an error" for the new check; the installer's older errors (a broken `models.<class>` list, a config that isn't JSON) still exit 1 through `throw`, as PKT-2 left them, and changing them is outside this packet. A test snapshots every file under `.github`, the manifest included, before a run with `-Force -WithInstructions` (which would otherwise rewrite the manifest and add the instructions file), and compares it after, for both `packet-reviewer-max` and `premium`.
9. **A plan-only run resolves no class.** It writes no agent and never reads `models` (PKT-2, decision 2), so a bad `models.agents` can't stop it either. `-PlanOnly` on a full install is still refused first.
10. **The installer's own class table stays, renamed `$agentFileClass`.** PKT-1's test reads the kit's classes from it (`'packet-….agent.md' = '<class>'`) and checks that `$script:AgentModelClass` agrees, so removing it would change an existing test. The classes written now come from `Get-PwAgentModelClass`; the table only gives an agent file a class on a plan-only run, where agents are filtered out anyway. It had to be renamed: PowerShell variable names ignore case, so `$agentModelClass` in the installer's script scope *is* the library's `$script:AgentModelClass` once the library is dot-sourced, and assigning the table overwrote the library's map. No other installer variable shares a name with one of the library's script variables.
11. **The "Agent models:" line is unchanged; a second line names each moved agent:** `Agent classes from models.agents: packet-dispatcher on standard (the kit's: strong).` It appears only when some agent's class differs from the kit's, so a default install's output is the same as before. A kept, hand-edited agent is still named in the "Agent models:" line as keeping its own `model:` line.

## The Local harness warning

12. **The rule:** classes rank light < standard < strong. The installer warns when a subagent's class ranks above `packet-dispatcher`'s **and** the two classes' lists differ (compared in order, case-sensitively). The subagents are the kit's other four agents, the ones in the dispatcher's `agents:` line. Equal lists can't differ in cost tier, so with the shipped lists (GPT-6.1 Sol first in every class) it never warns. A class above the dispatcher's whose list equals the dispatcher's isn't named either.
13. **The warning names each such agent with its class and list, the Local harness, the stop and both fixes:** in VS Code's Local harness, a subagent on a model in a higher cost tier than the session's doesn't run, so a review round that needs it stops at Needs human (PKT-6); to avoid it, run those dispatches in a session on the higher model, or give that agent the dispatcher's class in `models.agents`. It goes to the warning stream, after the "Agent models:" lines, so it doesn't break the summary. It is static: it reads the config, not the session's model, so it can only say the setup *can* stop a round.

## What the dispatcher on standard is worth

14. **With the shipped model lists, putting the dispatcher on the standard class costs nothing and saves nothing.** Every class lists GPT-6.1 Sol, then Claude Sonnet 5.5 (the owner's answer to question 1), so the dispatcher runs on the same model either way, and `creditsPerRun` (PKT-7's GPT-6.1 Sol rates) prices it the same. The solo overlay still sets it so that the saving arrives by itself once `models.strong` names a dearer model: the dispatcher then stays on the standard list, and the difference in rates is cost.md's lean change #8. In that setup the installer's warning applies, because the deep reviewer stays on the dearer strong list.

## Tests

15. **The tests are in `tests/cases/solo-install.tests.ps1`** (32 assertions), under PKT-1's case-file rules: plain variables, kit code only through `Invoke-Kit` and `Invoke-CaseProbe`, nothing dot-sourced, no `$script:` assignment. Each target is a fresh `git init` with a GitHub origin URL and `origin/HEAD` at `trunk`, in its own temporary folder, removed in `finally` (kept with `-Keep`). Nothing depends on time or on the order of hashtable keys, so the file is deterministic. `Get-PwConfig` runs on the written solo config through `Invoke-CaseProbe`.
16. **What isn't covered:** the warning's behaviour in a real Local harness session (PKT-9's e2e stages and H-4 check that), and output under a non-UTF-8 Windows console.

## Names that differ from the packet

- None of the consumed names changed: `Get-PwAgentModelClass`, `$script:AgentModelClass`, `install.ps1 -PlanOnly` and the manifest's `mode` are used as merged. `Merge-PwHashtable` is not used, for the reason in decision 2; the packet expected the installer to merge into an ordered copy.
