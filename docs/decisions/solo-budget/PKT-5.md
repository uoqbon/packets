# PKT-5 · Decision record

Choices [PKT-5](../../plan/solo-budget/packets/PKT-5.md) left open, and why each went the way it did.

## Where it reads, and in what order

1. **The arguments' shape is checked before anything is read.** A missing `-Packet`, `-Base` or `-Next`, a `-Next round` without all four of `-Round`, `-Tier`, `-Lenses` and `-Runs`, those four with another `-Next`, and `-Pr` with `-Next start` all exit 2, even when no ceiling is set. These are mistakes in the caller (PKT-6's instructions), and they don't depend on the repository, so an install without a ceiling still meets no failure that review-scope's own config read wouldn't hit. `-Packet`, `-Base` and `-Next` aren't `Mandatory`: under `pwsh -File` a missing mandatory parameter can prompt for input. The script checks them itself and exits 2. `-Next later` is a binding error and exits 1. `-Round`, `-Tier` and `-Runs` are taken as strings and must be whole numbers, so `-Round abc` and `-Tier 2.5` exit 2. As `[int]` parameters, `-Tier 2.5` would bind as 2 without a word (round-2 correctness review). Positional binding is off, so a stray argument is an error too, not a value for the first parameter.
2. **OFF reads only two configs: the one at the merge base and the one on origin's default branch.** The base's is read with `Get-PwConfig -Ref <merge base>`, as review-scope reads it, so a broken config fails here exactly as it fails there. The default branch's is read with `Get-PwSharedConfig`, from git, as board and progress read it (decision 3). OFF needs the ceiling unset in both. This goes beyond the packet's "after reading only the config at the base": the owner decided on PR #35 that the default branch's ceiling counts too, so an install whose origin doesn't report its default branch now stops here (exit 2), as board and progress already do. So does a clone with no origin, and an origin whose default branch has no config: `Get-PwSharedConfig` and `Get-PwConfig` would read the working tree there, the branch's own checkout, which would then decide who is trusted (round-2 security and integration reviews). Warnings from either config read go to stderr, so stdout holds only the result line or the JSON, and an OFF in `-Json` carries every field WITHIN has, as `null`. The test for "unset" is `Get-PwCreditCeiling`'s: `budget` isn't a table, has no `maxCreditsPerPacket`, or it is `null`. Get-PwConfig fills the defaults first, so a config written before 0.1.1, without the key, reads as unset. The packet file, `Get-PwSharedConfig`, the PR and the rates aren't touched, and a test checks that no `gh` call happens. The script has no `-ConfigPath`: the base and the default branch decide. A base with no `.github/packet-workflow.json` exits 2. Get-PwConfig would warn and read the working tree instead, which is the branch's own checkout, so a branch whose merge base predates the install could otherwise set its own ceiling. review-scope keeps that fallback for the install PR, which is no packet.
3. **Trust comes from origin's default branch; the ceiling and the price come from both it and the base.** The ceiling at the base and the ceiling on the default branch are both read for the packet's size at the base, and the stricter one holds (the owner's answer to open question 2 on PR #35). So a branch kept on an old base, from before a ceiling was set or lowered, can't loosen it, and a ceiling the owner lowers on the default branch reaches packets in flight at once. A ceiling that is set but broken on either side exits 2. The text line says `(config)` when the base's holds and `(config on origin/<branch>)` when the default branch's does; `-Json` adds `CeilingFrom`, `BaseCeiling` and `DefaultBranchCeiling`. The rates, `review.tierCap` and `review.lensesPerReviewer` come from the config at the merge base, and the packet's size from its file there. Who is trusted comes from `Get-PwSharedConfig`, as `board rounds` reads settles. So neither the branch nor an old base can add a trusted author. A test has the base trust `exmate` and the default branch not, and `exmate`'s raise changes nothing. **Pricing with both** (the owner's answer on PR #35 to the round-2 security review): the packet is priced twice, once with the base's config and packet file (rates, `review.tierCap`, `review.lensesPerReviewer`, size, Review tier line) and once with the default branch's, and the higher total holds, with its own so-far and step. So an old base can't lower the rates, the tier cap, the lens grouping or the size either. If the packet file is gone from the default branch, the base's stands in for that side. A rates typo on either side exits 2. `-Json` names the pricing that held (`PricedWith`: `base` or `default-branch`, the base on a tie) and gives both totals (`BaseTotal`, `DefaultBranchTotal`); the text line is unchanged.
4. **The PR must be the packet's own open PR.** Without `-Pr`, it is the newest open PR on a `pkt/<id>-…` branch. Unlike `board pr`, the script doesn't fall back to a closed one, since an abandoned attempt's markers would price this one. A PR given with `-Pr` (or `#21`) is read once over REST (`repos/<repo>/pulls/<n>`), and its branch must start `pkt/<id>-` and its state be open. Otherwise the script exits 2. Another packet's PR would bring in that packet's rounds and raises.
5. **Only `github-common.ps1` loads.** The script never loads a board provider, so an Azure Boards outage or an expired PAT can't stop a round check. Its only `gh` calls are the sign-in, `pr list` without `-Pr` or the PR itself with it, and the PR's comments. All of them read, and a test checks that none of them writes.

## What it prices

6. **Every number is `Get-PwCreditEstimate`'s.** So far is the estimate over the PR's trusted round markers. The total is the estimate over those markers plus one more row for the step, and the step is the difference. So the check prices exactly as `progress.ps1 -Credits` does, rounding included: round 2 in the acceptance test is 394.5, booked as 394. `-Next start` has no PR, so so-far is 0 and the step is the whole total. The comparison is `total <= ceiling`: equal is WITHIN.
7. **The step's row.**
   - `-Next start`: round 1, one lens, one run, no fix, at tier 1, or at the packet's **Review tier** line at the base when it has one: review-scope raises round 1 to that line, so tier 1 would underprice such a packet (round-2 correctness review).
   - `-Next round`: the arguments as given, with `-Lenses` counted as review-scope counts lenses: lower case, each once, and a run name such as `security+data` is two. `-Tier` takes 1 to 3, the tiers review-scope prints. `-Runs` takes 1 up to the number of lenses, since review-scope never prints more runs than lenses. `-Round` must be one more than the last round marker, or 1 with none.
   - `-Next fix` after `outcome=fix`: round N+1 at the last round's tier plus one. The +1 stops at `review.tierCap`, or at 3 with no cap, but the tier never drops below the last round's, as review-scope carries it as merged in PKT-3 (its decision 5): under cap 2 a tier-3 round is followed at 3. A forced reason in the diff can lift the cap, which only makes the real round dearer than the cheapest one priced here; the round check still catches it. The lenses are that round's `confirmed=` list (counted the same way), in `ceil(lenses / review.lensesPerReviewer)` runs: the fewest runs review-scope can give them. With no confirmed lens (a `confirmed=-` fix, which review-scope would still review with correctness), it prices one lens. A marker with no tier, or `tier=4`, counts as 3, as the estimator prices it.
   - `-Next fix` after `outcome=pass` (a CI fix, §9.3), or after `outcome=needs-human` (a fix the owner asked for in answer; the owner's answer to open question 1 on PR #35): round N+1 at that round's tier, never capped below it, one lens, one run, with `outcome=fix` on the row. That makes the estimator book `implementerFix` for the CI fix run, which no real marker will.
   - `-Next fix` after any other outcome, or with no round marker yet, exits 2.
8. **Settle and budget rows are never priced.** `Get-PwRoundRows` leaves them out, as before. So a budget raise can't change an estimate, and the tests check that for `Get-PwCreditEstimate` and `Get-PwCreditSummary`.

## The raise

9. **Only the newest trusted `packet:budget` comment counts, wherever it sits among the rounds.** The marker must be the comment's first words. A trusted comment that quotes one lower down, such as test output or a diff, which this packet's own test file is full of, raises nothing. It can come before or after later rounds, and it holds for the rest of the packet (question 5). An older raise is ignored, broken or not. So if the owner mistypes a raise, a corrected comment fixes it, and they don't have to delete the first. If the newest raise's `max` isn't a whole number from 1 to 999,999,999 (`^\d{1,9}$`, above 0), the check exits 2 and names the comment. A number that size can't overflow, and no real ceiling comes near it.
10. **A raise only raises.** A `max` at or below the ceiling in force (the stricter of the two configs') leaves the ceiling and its source (`config`) as they were. A higher one replaces it, whichever config the ceiling came from. "Only raises" is measured against the config, so a newer raise below an older one, but above the config, lowers the limit to the newer value: the newest wins, as question 5 has it. The owner confirmed this on PR #35, and tests pin it: `max=3000` then `max=1000` gives a ceiling of 1000, and `max=3000` then `max=800` under a ceiling of 900 leaves 900, because the older raise is dropped with it. When it is raised, and the line ends `(raised by <login> <yyyy-MM-dd>)`, with the date in UTC from the comment's `created_at`. `-Json` also carries `ConfigCeiling`, `RaisedBy` and `RaisedAt`, with whole numbers as JSON integers.
11. **Budget rows in `Get-PwGhRounds`.** A trusted comment whose body starts with the marker (after white space, as a code span or `<code>`) gives a row. Each row gets `Kind = 'budget'`, `Outcome = 'budget'` and `Round` set to the last round so far, as settle rows have them. `Head`, `Tier`, `Lenses`, `Runs`, `Confirmed` and `Body` are `$null`, and `Consumed` is `$false`. `Max` is the marker's `max=` value as written, a string, or `$null` when there is none. The reader checks it, not the row builder. That way `board rounds` still shows a broken raise to the owner, and a typo can't stop `board rounds` or `progress -Credits`. `board rounds` prints `budget <round> max=<n> by <login>`. Its other lines are as they were.

## Tests

12. **GitHub is stubbed as a `gh` function, one call below `Invoke-PwGh`.** The packet asks for the stubs the "trusted round reader" tests use (`Invoke-PwGh`, `Invoke-PwGhPages`). But `credit-check.ps1` and `board.ps1` load `github-common.ps1` themselves, which would replace those two stubs. A case file also may not dot-source `github-common.ps1` (PKT-1's case-file rule), so the stub moves down one call. It is a `gh` function defined in the `Invoke-CaseProbe` child, which `Invoke-PwGh`'s `& gh` finds ahead of any `gh` on PATH. The real `Invoke-PwGh`, `Invoke-PwGhPages` and `Get-PwGhRounds` run unchanged. The stub logs every call, fails when a test says so, and fails any call it doesn't know. Everything runs offline.
13. **The tests set their own rates.** Each test base writes 0.1.1's `creditsPerRun` into its own config, so PKT-7's change to the defaults can't move them. The fixed numbers (620, 394, 1014) appear only where the packet gives them. Everywhere else the expected value comes from `Get-PwCreditEstimate`, run in a probe with the same config and rows.

## Lens review

14. The security, integration, correctness and tests reviews of the diff led to decisions 2, 4, 7, 9 and 10 as they now read: the base must have a config, the PR is checked, lenses are counted as review-scope counts them, the marker must open the comment, and the JSON numbers are integers. After PKT-3 merged, the fix-round tier follows its carry rule (decision 7). They also led to tests for each, and the fix-round test now uses two confirmed lenses, so the confirmed list and `lensesPerReviewer` both change its price. The owner's answers to the PR's open questions led to decision 3's second ceiling and decision 7's fix after a Needs human. Not taken: a check in `-Next start` that no PR exists yet, which would make an extra `gh` call where the packet has none.

15. **Second review round** (security, integration, correctness and tests, over the whole diff after the owner's answers). Nothing blocking. Fixed: no origin, or no config on its default branch, now exits 2, since the working tree would otherwise decide who is trusted (decision 2); config warnings go to stderr, so `-Json` parses; an OFF in `-Json` carries every field; `-Round`, `-Tier` and `-Runs` must be whole numbers (decision 1); `-Next start` prices round 1 at the packet's Review tier line (decision 7). The security review's point that an old base still set the rates, cap and size went to the owner, who chose pricing with both configs (decision 3). The tests review ran 18 mutations of the code; all were caught but two, and tests now cover both: a raise between the two ceilings, and a `max` of 0, ten digits, a negative number or none. Known limitation, as for board and progress: origin's default branch is read as this clone last fetched it.
